# 技术债 #4 方案：覆盖升级预检工具（upgrade_guard）

量测日期：2026-10-19｜上游 v2.7.0 目录在本地，可实测比对

---

## 一、问题（已量测，非推测）

官方便携包"覆盖升级"会直接替换我们**同名**的文件。实测数据：

| 类别 | 数量 | 影响 |
|---|---|---|
| **同名但内容不同**（会被冲掉） | **40 个** | 🔴 含 `main.py`、`paper_helper.py`、`static/js/{import,paper,editor,api,ocr}.js`、`static/css/app.css`、`static/index.html`、`mathbank/{db_migrations,database,prompts,...}.py` |
| 我们独有（安全） | 138 个 | 🟢 `pdf_local_split.py`、`parsing_pipeline.py`、`routes_*.py` 全套等 |

**另两个已核实的事实：**

1. **`scripts/release_overlay.py` 挡不住这件事**。它是上游官方机制，但它的 `protected_paths` 只有
   `.env` / `.system_generated` / `data_backup` / 数据库文件 / `static/uploads` / `venv`
   —— **一个源码文件都不保护**。且它被启动器自动调用，是"安装后对账"，不是"安装前预警"。

2. **仓库里没有任何上游 diff 脚本**。技术债原文说的"升级前必须先跑 `scripts/` 侧 diff 报告"
   —— 这个脚本**根本不存在**。

---

## 二、关键发现：manifest 里有每个文件的 sha256

`E:\math-question-bank\RELEASE-MANIFEST.json`（上游自带）：

```json
{
  "app_version": "2.7.0",
  "platform": "windows-x64",
  "schema_version": 1,
  "overlay": {
    "managed_roots": ["main.py", "mathbank", "scripts", "static", "templates", ...],
    "protected_paths": [".env", ".system_generated", "data_backup", ...]
  },
  "files": [ {"path": ".env.example", "sha256": "...", "size": 1717}, ... ]   // 1726 条
}
```

**这让我可以做三方比对，而不只是"警告"：**

对每个即将被覆盖的文件，有三种情况：

| 情况 | 判据 | 处置 |
|---|---|---|
| **A. 我们没改过** | 我们的 sha256 == 升级包里的 sha256 | 安全，直接放行 |
| **B. 我们改过，上游也改了** | 双方 sha256 都 ≠ 上一版基线，且互不相等 | **🔴 必须人工合并**（最危险，会丢我们的二开） |
| **C. 我们改过，上游没改** | 我们的 ≠ 包里的，但包里的 == 我们记录的"上次同步基线" | 🟡 我们的改动会被冲掉（可自动备份还原） |

**C 类是可自动化的**（备份后可还原）；**B 类必须人工**（要合并）。

而 `installed-release-manifest.json`（`release_overlay.py` 会写）
正好记录着"我们当前装的是哪一版"，可作为三方比对的**基线来源**。

---

## 三、方案：`scripts/upgrade_guard.py`

### 定位
**只读预检工具，绝不修改任何文件。** 在解压升级包**之前**跑，输出人可读报告。

### 用法
```powershell
# 对着新下载的便携包（未解压目录或已解压目录都行）
.\venv\Scripts\python.exe -m scripts.upgrade_guard E:\下载\mathbank-2.8.0
# 或直接指定 manifest
.\venv\Scripts\python.exe -m scripts.upgrade_guard --manifest E:\下载\新包\RELEASE-MANIFEST.json
```

### 输出三张清单

1. **🔴 冲突清单（B 类）—— 必须人工合并**
   列出：相对路径、我们的 sha256、升级包的 sha256、双方大小差异、**我们能提供的辅助信息**（行数差）。
2. **🟡 将被冲掉清单（C 类）—— 可自动备份**
   我们的改动会丢，但有备份可还原。
3. **🟢 新增/安全清单**
   升级包有、我们没有的（**这是新功能，值得看**）；以及双方一致的。

### 报告头部（可追溯）
- `git rev-parse --short HEAD`（我们的代码状态）
- 我们当前 `__version__` 与升级包 `app_version`
- manifest 的 `platform`、`files` 条数、manifest 自身 sha256
- 比对时间戳

### 额外价值：升级包带来了什么新模块
列出"升级包有、我们没有"的文件，并**按目录聚合**。
实测这批里就包含 `mathbank/source_metadata.py`、`word_hybrid_plan.py`、`docx_source_*.py`
—— 正是 Word 快路径链路。**diff 报告能提前告诉我们"上游有这些新能力要不要接"。**

## 四、严格边界

1. **只读**。不写任何文件、不修改 manifest、不碰 `.env`/数据库。
2. **不改 `release_overlay.py`**（那是上游文件，改了会被下次升级冲掉，且属红线）。
3. **不自动合并**。B 类只报告，不猜意图 —— 自动合并代码是灾难。
4. **不依赖网络**。只读本地升级包 + 本地仓库。
5. 找不到 manifest 时**明确报错**而不是猜（`该目录不是 MathBank 便携包：缺 RELEASE-MANIFEST.json`）。

---

## 五、测试

用**上游目录本身**做 fixture（它自带真 manifest），断言：
1. 能正确解析 manifest（1726 条、platform、version）。
2. 对我们的仓库跑一遍，**40 个同名冲突必须全部出现在报告里**（钉住"不许漏报"）。
3. 138 个独有文件**不得**出现在冲突清单里（钉住"不许误报"）。
4. 纯只读：跑完后仓库文件 mtime 与 sha256 全不变。
5. 缺 manifest 时报错且退出码非 0。

## 六、不做的事

- **不做"二开文件改名/独立目录"那个长期方案**。技术债原文提了，但那是**大重构**：
  要把 40 个文件改名或移位，牵动 import、构建、启动器、以及 1659 条测试。
  与"下次升级前必须定策略"这个时间要求相比，**预检工具是 90% 收益 / 2% 成本**。
  改名方案应在预检工具用一段时间、看清真实升级频率后再评估。
- **不做自动升级**。升级动作本身该由人确认。
