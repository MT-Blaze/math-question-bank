## 2. 超宽公式横向滚动 —— 已移植，只覆盖选择题选项

**也不是"待抄作业"。**

`static/js/editor.js:1939-1961` 已实现，注释明确写着「移植自上游 V2.7.0」：
- 策略：1 列 + 缩字号到 FLOOR 仍装不下 → 给那条公式加 `.choices-math-scroll`
- `static/css/app.css:831-838` 配套 CSS，注释交代了关键点：`display` 必须是 `inline-block`（overflow 对非替换内联元素无效，KaTeX 的 `.katex` 是 `inline-block` 才成立）

**真实缺口**：选择器是 `.choices-grid .choices-content .katex.choices-math-scroll`——
**只管选项，不管题干、不管填空题、不管解答题。**
题干里一条超长公式（比如长分式链、长矩阵）目前没有横向滚动，只能撑破或缩到看不清。

**判断**：改动量小（复用一个类 + 扩选择器），但**要先确定期望行为**：题干超宽是"横向滚动"还是"保持折行"？这涉及学生的阅读体验，得你拍板。

## 3. 抽离成纯净模块提 PR —— 代码已纯净，真正的障碍不是代码

**这是我唯一想劝你别急着做的。**

代码纯度**已经达标**：
- `mathbank/pdf_local_split.py`（319 行）：只 import `re` / `dataclasses` / `typing`，**顶层绝不 import main**（文件头注释专门交代了原因：会触发 main 抢 runtime 锁）
- `static/js/virtual_list.js`（353 行）：零依赖，只挂 `window.MathBankVirtualList`，文件头注释交代了"为什么必须手写"

**但提 PR 的真实障碍有三条，全都不在代码里：**

1. **上游版本坐标不一致**。我们的 `mathbank/` 是重构后的 62 个模块，上游 `main.py` 是单文件 270KB + 少量 `mathbank/`（见 `outputs/上游v2.2.3对比分析.md`）。**我们的 `routes_paper.py` 结构，上游根本不存在**。PR 过去等于要上游先接受我们的模块化改造。

2. **schema 版本差 16 级**。我们 v26（本轮后），上游 v10。`pdf_local_split` 本身不碰 schema，但**PR 的上下文会牵扯迁移链**，评论里必然被问。

3. **`pdf_local_split` 依赖我们的 `mathbank/pdf_inspector_helper`**（`_has_math_formula_loss` 探测），且是 **try/except 降级**导入。上游没有这个模块——这意味着 PR 必须自带一个可选依赖声明，否则上游一 import 就报错（虽然被 except 兜住，但功能够就残了）。

另外，`virtual_list.js` 挂的是 `window.MathBankVirtualList`，名字带项目前缀，上游接过去要改名——**上游会不会愿意维护一个"为离线零构建架构特化"的虚拟滚动器**，也是未知。

**判断**：**这不是技术任务，是社区协作任务。** 建议先做**零成本的试探**：给上游开一个 issue，附 `pdf_local_split.py` 的设计说明 + A 档 88.9% 数据 + 那三个问题，看对方反应再决定要不要投入抽离工作。**issue 的成本是 10 分钟，PR 的成本是一周。**

## 4. 导出自愈层 Toast —— 这里才是真缺口

**这条有实实在在的洞。**

现有机制完整且设计得不错：
- 后端 `mathbank/latex_preflight.py::repair_latex_before_compile` 修复编译前 LaTeX
- 结果经 `X-MathBank-Export-Notes`（URL 编码）+ `X-MathBank-Export-Note-Count` 响应头回传
- `_export_notes_headers`（`routes_paper.py:2405`）带长度护栏（注释交代了「40 题长卷能把头撑到近 10KB，会被代理层掐掉」）
- 前端 `paper.js::notifyPaperExportNotes`（`:3206`）翻成 Toast

**缺口一：Word 导出这条完全没接。**
`export_paper_word`（`routes_paper.py:2708`）只发 `X-Word-Native-Formulas` / `Fallback` / `Failed` / `Missing-Images` 等头，**没有 `X-MathBank-Export-Notes`**。前端 `exportPaperWord` 也没调 `notifyPaperExportNotes`（只在 `:3271` / `:3755` / `:3770` / `:4166` 四处调，全是 LaTeX/PDF 侧）。

后果：同一道题，导 PDF 会提示「已自动修复 3 处公式问题，请回题库核对」，导 Word **一声不响**——但 Word 侧同样有 `failed_formulas` 落成红字。**用户在 Word 里看到红字，却不知道要去改原文。**

**缺口二：`_export_notes_headers` 已有 3 处调用（tex/bundle/pdf），但讲义侧走的是另一条路。**
`routes_lecture.py:325` / `:355` 自己拼头。`lecture.js:66` 自己读头。→ 两条实现，将来必然漂移。

**缺口三：`X-MathBank-Export-Notes-Shown` 这个头后端已经在发（`:2431`），前端 `notifyPaperExportNotes` 没读它。**
后端特意给「实际展示条数」，前端却只读了 `-Count`。→ 当笔记超长被截断时，Toast 说的是总条数，用户以为全看到了。

**判断**：缺口一有真实用户可见后果（Word 红字无解释），缺口二三是隐患。**改动量小、风险低、立刻可验。**

## 5. 优先级建议

```
先打 #4（导出自愈 Toast 接全）    ← 有真实用户可见缺陷，半天可收
顺手带 #1 的 Word 逐图尺寸        ← 同一个文件（Word 导出链），一次改完
再议 #2（题干超宽滚动）            ← 等你定行为：滚动 or 折行
最后 #3（提 PR）→ 先开 issue，不直接 PR
```

**为什么 #4 优先于 #1**：
两者都指向 Word 导出，但 #4 是"该说的没说"（用户困惑），#1 是"排版不一致"（用户可能还没用到逐图排版按钮）。#4 的修复还能顺手把 #1 的 Word 链路一起摸熟，**一次进入同一个文件，做完两件事成本更低**。

**为什么 #3 垫底**：它不改善本项目任何东西，收益全在上游。而 issue 就能拿到 90% 的信息价值。
